## Histórico de decisões

- 2026-08-03: Projeto Angular 19 gerado (`ng new`, standalone components, routing, SCSS, Jasmine/Karma) para viabilizar o ciclo TDD dos tickets.
- 2026-08-03: `environments/` criado e `AuthService` atualizado para usar `apiBaseUrl` (`https://localhost:7002` local) após CORS ser habilitado no backend localmente. Suíte (16/16) e build de produção confirmados verdes após a mudança.
- 2026-08-03: `docs/design/mockup.pdf` adicionado (1 página, tela de Dashboard/Painel — não é mock de login). Spec do MVP-1 atualizada: rota raiz `/` agora também renderiza `LoginComponent` (tela inicial temporária do MVP, critério de aceite 6) e a tela de login foi restylizada extraindo o design system do mock (cores, logo/mascote, tipografia, estilo de card/botão — tokens em `src/styles.scss`). Reaprovado pelo QA — 18/18 testes, build limpo.
- 2026-08-03: Bug encontrado pelo usuário testando no navegador — `app.component.html` tinha `<router-outlet />` enterrado depois de ~300 linhas de marketing padrão do `ng new`, escondendo a tela de login. Corrigido (template agora só `<router-outlet />`); teste de regressão com asserção negativa adicionado. QA reaprovou — 17/17.
- 2026-08-03: Interceptor `src/app/core/interceptors/auth.interceptor.ts` implementado, fechando o critério de aceite 1 (anexação automática de `Authorization: Bearer <token>` nas rotas autenticadas). Uma primeira versão excluía indevidamente `GET /api/user` (só `POST /api/user` é público) — corrigido para exclusão por método+path. QA aprovou — 24/24 testes, build limpo. **MVP-1 agora está completo end-to-end** (rota, visual, e anexação real do token).
- 2026-08-03: MVP-2 (Dashboard de Transações) concluído via ciclo `po` → `dev-frontend` → `qa` — spec em `docs/specs/mvp-2-dashboard-transacoes.md`, `TransactionService` + `TransactionsComponent` (listar/criar) implementados, rota `transactions` adicionada. `categoryId` deixado fora da UI de propósito (depende de MVP-3, ainda Backlog). QA aprovou de primeira, adicionando 2 testes próprios de cobertura — 50/50 testes, build limpo.
- 2026-08-03: Bug reportado pelo usuário testando no navegador — login não parecia redirecionar após sucesso. Causa: `login.component.ts` navegava para `'/'`, rota que desde o MVP-1 também renderiza `LoginComponent` (era placeholder temporário antes de existir uma tela real pós-login). Corrigido para navegar a `/transactions` (a tela entregue pelo MVP-2); teste ajustado para checar a URL exata. 50/50 testes, build limpo.
- 2026-08-03: **Bug crítico de contrato encontrado pelo usuário** — POST `/api/transaction` retornava 400 (`"The JSON value could not be converted to ... TransactionType"`) mesmo com payload aparentemente correto. Investigação via `/swagger/v1/swagger.json` e chamadas reais à API local revelou que `docs/api-contract.md` estava **errado desde a origem**: todos os enums (`TransactionType`, `PaymentMethod`, `CardBrand`, `UserType`) trafegam como **número**, não como string literal, e todo campo `*Id` (`userId`, `transactionId`, `categoryId`, `creditCardId`, etc.) é **número**, não string. Isso nunca foi pego pelo `qa` porque MVP-1 e MVP-2 foram validados só com specs mockadas (`HttpTestingController`/spies), nunca contra a API real. Contrato corrigido primeiro (mapeamento nome↔número documentado, com nota explicando a correção e a evidência), depois `enums.model.ts` (union types → `enum` numérico), `auth.model.ts` e `transaction.model.ts` (`*Id` para `number`), `transactions.component.ts/html` (selects agora usam `[ngValue]` + labels em PT-BR, comparações de enum corrigidas, bug de falsy-check em `paymentMethod` — `Pix = 0` era tratado como "não informado"), e todos os specs afetados (`login`, `auth.service`, `transaction.service`, `transactions.component`). Validado com chamada real ao endpoint reproduzindo o payload exato reportado pelo usuário (`type: Saida`, `paymentMethod: Transferencia`) — agora recebe 200. 50/50 testes, build limpo. **Risco residual**: como a API real segue indisponível para o `qa` automatizado validar (specs de todos os tickets usam mocks), qualquer novo endpoint/campo deve ser conferido contra o swagger real antes de fechar o ticket, não só contra este documento.
- 2026-08-03: Spec do MVP-2 (Dashboard de Transações) escrita pelo `po` em `docs/specs/mvp-2-dashboard-transacoes.md`, cobrindo `GET/POST /api/transaction` com os DTOs `TransactionRequest`/`TransactionResponse`/`TransactionResponseList` e enums `TransactionType`/`PaymentMethod` do contrato. 12 critérios de aceite (listagem: sucesso, vazio, erro de rede; criação: sucesso com/sem opcionais, validações client-side, erro 400, erro de rede). Decisão: seleção de `categoryId` e exibição de nome de categoria na listagem ficam fora de escopo por dependerem de `GET /api/category` (MVP-3, ainda em Backlog) — a listagem/criação deste ticket trabalha só com os campos literais do contrato. Ticket movido para fase `Spec`.
- 2026-08-03: MVP-2 (Dashboard de Transações) implementado pelo `dev-frontend` em TDD estrito a partir da spec: `src/app/core/models/transaction.model.ts` e enums `TransactionType`/`PaymentMethod` em `enums.model.ts` espelhando o contrato; `src/app/core/services/transaction.service.ts` (getAll/create via `environment.apiBaseUrl`); `src/app/features/transactions/transactions.component.ts` (listagem + formulário de criação, validador customizado `positiveNumberValidator` para `value`, payload omitindo campos opcionais não preenchidos em vez de enviar `null`/string vazia); rota `transactions` adicionada em `app.routes.ts`. `categoryId` não exposto na UI (depende de MVP-3, Backlog), conforme escopo da spec. QA validou de forma independente os 12 critérios de aceite e encontrou uma lacuna de cobertura (asserção de DOM ausente confirmando que os `<select>` de `type`/`paymentMethod` oferecem exatamente os literais do contrato, sem texto livre) — adicionou 2 testes ele mesmo para fechar o gap, sem necessidade de retrabalho do dev. Suíte final 50/50, build limpo. Aprovado — MVP-2 concluído sem nenhuma rodada de rejeição.
